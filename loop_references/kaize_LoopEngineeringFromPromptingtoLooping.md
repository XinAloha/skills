循环工程——从提示词到循环运转
我想把这篇内容献给你：如何亲手打造一个可编程的智能体，让它替你完成日常工作。这样一来，你就不必每天早上打开电脑，反复敲指令给它了。

它会自己醒来，自己找活干，自己判断什么问题值得解决，最后把结果整理好放在你面前，只等你来拍板。

前言
Loop 这个想法不是凭空冒出来的——2026 年 6 月那一周，三位行业大佬几乎在同一时间表达了相似的观点：是时候往这个方向发力了。

一周后，Andrew Ng 把这场讨论放进了“从 0 到 1 做产品”的更大框架里，给了我们更完整的视角。

这篇文章就从那个故事讲起，然后一步步带你 从零搭建一个最小但完整的循环：5 个动作、6 个部件、一扇能说“不”的闸门，以及一扇专门留给人的门。整套东西可以跑在你自己的机器上，也能复用到任何软件项目里。

实践比命名早了好几个月——大家早就在写循环了，只是没人给它起个正式名字。

如今，“循环”已经成为我们让 AI 智能体长期迭代、持续产出软件的关键手段。

Andrew Ng 按时间尺度把三个循环从内到外排列：最内层跑得最快，最外层跑得最慢。而且，最外层的输入恰好来自最内层的输出：

循环	谁在跑	周期长度	向外层输出什么
智能体编码循环	智能体自己	秒～分钟	一个能跑起来的版本
开发者反馈循环	人类 + 智能体	十分钟～小时	更清晰的产品愿景和规格说明
外部反馈循环	用户 + 团队	小时～周	推动愿景演进的真实数据
Andrew Ng 给了我们一张按时间划分的地图：三个循环以不同速度并行运转。Addy Osmani 则画了第二张按抽象层次划分的地图：提示 → 上下文 → 工具集 → 循环。

循环工程处于最顶层，它在工具集之上额外加了三个本事：按定时器跑、生成辅助任务、自身产出回流——今天的输出自动变成明天的输入。最后这一点，才是它被称作“循环”的根本原因，而不只是“把同一个任务重复跑 N 遍”。

最核心的一条直觉：同样的 bug，在不同层面去修，成本天差地别：

层面	关注什么	核心问题
提示工程	怎么写提示词	对模型说什么
上下文工程	窗口里塞了哪些内容	取什么、摘要什么、清掉什么
工具集工程	单次运行的装备	哪些工具、哪些动作、什么算“完成”
循环工程	在工具集之上做调度	怎么让它自己一轮一轮地跑下去
循环从设计之初，就是冲着“运行轮次可以很大”去的。此后的一切决策——评估器、人工闸门、令牌上限、状态文件——全都在做同一件事：缩短从“错误发生”到“有人发现”的距离。

每一轮内部发生了什么？
很多人把“循环”误解成“原地空转”。其实不是的，每一轮都有 5 个具体动作。少掉任何一个，循环要么根本跑不起来，要么跑了也白跑。

验证是那个敢说“不”的动作。

调度是把这一轮喂给下一轮的动作。

恰恰是这一步，才让循环真正成立。

对应到我们即将搭建的项目——一个面向小团队的晨间分流循环：

动作	做什么	在分流循环里对应什么
发现	决定这一轮该干什么	一个技能去读 CI / 议题 / 最近提交
交接	派发任务，并把它隔离起来	每个发现单独开一个工作树
验证	换另一个智能体来说“不”	一个子智能体当审阅者，跑测试、挑毛病
持久化	把状态写到对话之外	PR + Linear 工单 + ./state/triage.md
调度	让它一轮接一轮自动跑	GitHub Actions 定时任务，早上 06:00 触发
下面 5 节课，每节专门强化一个动作。

五节课 = 一个完整的循环。

我们从第一课开始：发现。因为如果循环连“今天什么值得干”都定不下来，后面全白搭。

第 1 课 发现：写一份 morning-triage 的 SKILL.md
用“技能”，而不是堆提示词。
想象一下，周一早上 6 点，你的笔记本合着，GitHub Action 被唤醒，执行 claude --skill morning-triage。它读什么、怎么判断哪些事可做、结果写到哪里——所有这些都写在你即将编写的 SKILL.md 里。

Osmani 的关键洞察是：自动化应该触发一个技能——一份写下来的、可随时更新的项目知识，而不是一大坨贴在定时任务里的提示词。贴进去的提示词只会慢慢烂掉，因为没人会回头去更新埋在调度脚本深处的东西。

本课的任务：在 .claude/skills/morning-triage/SKILL.md 里写一个技能。要求它自己读取三个数据源（CI / 议题 / 提交），自己判断什么值得干，把结果写入 ./state/triage.md，并且在文件里明确写出 “红线”部分，规定这个循环绝对不能做什么。

下面是一个起步模板，改三处就是你的：

markdown
# .claude/skills/morning-triage/SKILL.md
---
name: morning-triage
trigger: invoked by daily automation
---

## 读取   （发现阶段的输入——换成你仓库里实际有的数据源）
- 自上次运行以来失败的 CI 任务      # gh run list --status failure
- 过去 24 小时内新建的议题          # gh issue list --search "created:>=…"
- 昨天以来合并的提交                # git log --since=yesterday
- 上一份 ./state/triage.md         # “昨天 → 今天”的交接信息

## 研判  （天花板——让循环自己挑，不要给它递清单）
对每个候选事项，判断：
- 现在能动手吗，还是纯属噪音？
- 会不会阻塞发版？ → 优先级标为 P0
- 已经在跟踪了吗？ → 跳过
只保留今天值得单独开一个工作树的事项。

## 落盘  （持久化——落到 markdown 里，别只留在对话窗口）
追加到 ./state/triage.md：
| 事项 | 来源 | 优先级 | 状态 |
提交这个文件，让明天能读到它。

## 交接  （为第 2 课做准备）
对每个保留下来的事项，输出一行任务描述：
  worktree=fix/<短标识>
  goal=<终止条件>

## 红线   （唯一不是样板的部分——请认真想清楚）
永不合并。永不删除。
任何拿不准的内容 → 放到 ./inbox/ 里，等人来定夺。
不许直接发 PR。
三个部分承担了真正的工作：

读取：这是发现的输入——列出具体的数据源，精确到实际命令。记住，“读一下上下文”不叫数据源，但 gh run list --status failure 是。

研判：这是整个循环的天花板。循环要自己区分“可动手”和“纯噪音”，而不是你每天早上递一张清单给它。因为如果你还在亲手递清单，那你只是自动化了“执行”，却没有自动化“选择”。而“选择”往往才是更贵的那一步。无论你的数据源多好，只要这一步捡了垃圾，后面四个动作就全是在无价值的事情上空转。

红线：这份文件里唯一不是样板的部分。循环会执行技能里写的一切，也只会执行技能里写的。如果你不写“永不合并”——总有一天它会自作主张帮你合并。

把红线写清楚：永不合并，永不删除，永不直接 push 到 main，任何拿不准的东西丢到 ./inbox/ 给人看，而不是直接进 PR。

还有一点值得提：同样的技能结构不限于晨间分流——把“读取”部分换成“昨天的访问日志 + 新议题 + 当前部署版本”，它就变成了晚间站点健康巡检；在“研判”里加一行“这是不是昨日的回归？”——它就拥有了跨日对比能力。

本课预防的陷阱：盲目循环
最常见的一种“看起来像循环，实际不是”的情况：循环在跑，但你每天早上还在给它分配任务（“嘿，看看这三个 bug”）。这是“执行自动化”，不是“发现自动化”。

症状：循环永远不会让你意外，因为它只做你早就知道该做的事。

修复：把“研判”放进技能里，让它自己挑选今天要干的事。

继续之前，回答这三个问题：
你的“红线”部分有几行？
如果只写了“永不合并”——再加一条：这个循环还绝对不能替你做什么？（永不关闭议题 / 永不推送到 main / 一次最多只取 3 个事项……）

把“读取”部分的第一条重写成一条在你的项目里真的能跑的命令。

如果这个技能一年都不变，会发生什么？
再对比一下：贴在定时任务里的那堵提示词墙，一年后会怎样？

第 2 课 交接：派发任务，并做好隔离
第 1 课的技能刚跑完。./state/triage.md 里现在躺着 5 个可操作的事项。最自然的想法是——同时启动 5 个智能体，分头推进，速度拉满。但这一步恰恰是“缠结循环”的起点：多个智能体在同一目录里改同一批文件，合并那天直接变成考古现场。

解药只有一条：每个事项单独开一个工作树。

git worktree 是 Git 的内置机制：一个仓库，多个独立的工作目录，每个目录单独 checkout 到一个分支。git worktree add ../fix-auth fix/auth 会在 ../fix-auth 开一个完全隔离的工作区。构建、编辑、测试——互不干扰。一个事项一个工作树 = 智能体在物理上被隔开。

本课的任务：写一个脚本，从 ./state/triage.md 里读取每个事项，为每个事项创建一个独立的工作树（命名 fix/<短标识>），派一个智能体在里面起草修复方案——并且设置并行上限，别让它无限制地往外冒。

bash
# 读取 state/triage.md，每个事项建一个工作树
# 修改：MAX_PARALLEL 设成你的机器 / 账单能扛住的数量
MAX_PARALLEL=3

# 修改：解析逻辑要匹配你实际的 triage.md 列
findings=$(awk -F'|' 'NR>2 && $5 ~ /open/ {print $2}' \
           state/triage.md | head -n $MAX_PARALLEL)

for finding in $findings; do
  slug=$(echo "$finding" | tr ' ' '-' | tr -cd '[:alnum:]-')

  # 关键操作：每个智能体物理隔离
  git worktree add ../wt-$slug -b fix/$slug

  # 修改：goal 是第 3 课评估器要读的终止条件
  claude --worktree ../wt-$slug \
    --goal "tests in tests/$slug pass and lint is clean" \
    "draft a fix for: $finding" &
done

wait   # 等所有并行的智能体跑完

# 收尾规则：智能体永不自动合并——工作树等着
# 第 5 课的人工闸门来放行
echo "所有工作树已就绪，等待审阅："
git worktree list
这里有几条铁律：永远不要直接在 main 上干活。

main 是给人审阅用的“降落跑道”，不是智能体的工作台。所有智能体统一在 fix/* 工作树上干活。

限制并行数：无限衍生是令牌爆表的前门（第 5 课会回来讲）。MAX_PARALLEL 的选择要基于一个诚实的问题：不是“我的机器能跑多少”，而是“我一天能审得过来多少个 PR”。

合并是人说了算：Stripe 每周通过这种循环跑 1000 多个 PR，但每个 PR 仍然由人审阅。人没有离开流程——只是换了工位：从“写代码”变成了“审代码”。

顺便偷师一个 Stripe 的细节：他们反直觉地用了更小的模型加上严格的确定性门控，而不是直接上最大的模型。

教训就是：在循环型任务里，一个严格的验证闸门，比粗暴堆模型参数要管用得多。

本课预防的陷阱：缠结循环
单智能体循环看起来一切正常。问题只在并行化的那天暴露出来——五个智能体跑完，五份 diff 在同一份文件里撞车，合并现场一片狼藉。

修复：每个任务独享自己的工作树，绝对不让智能体共享工作目录。

你把 MAX_PARALLEL 设成了多少？为什么？
（因为钱？因为机器性能？还是因为“我能认真审阅的 PR 上限”？）

如果某个工作树跑崩了——智能体直接退出，什么都没动。
明天的状态文件应该怎么记录这件事？

Stripe 用了更小的模型 + 严格确定性门控，而不是最大的模型。

第 3 课 验证：装一扇敢说“不”的闸门（分量最重的一课）
这是循环工程里最难的一步，值得比其他任何部分投入更多精力。

Anthropic 的工程师 Prithvi Rajasekaran 在捣鼓长期运行的智能体应用时发现：让一个智能体给自己刚写好的代码打分，它几乎永远在夸自己——哪怕人一眼就能看出写得不咋地。

这倒不是模型笨，而是：给自己的作业打分，这个结构本身就烂透了。 代码一写完，智能体的上下文里已经塞满了它为什么要这么写的自我辩护链条。它看自己的产出时，看到的不是“结果”，而是“我为这个结果打的辩护”。

把这个机制塞进循环里，就是一场灾难的放大器：每一轮的“够好了吗？”都由刚写完代码的那个智能体来回答。每一轮它都冲自己点头。跑得越久，离真实质量就越远。这就是点头循环——也是整个清单里最贵的一种坑。

Rajasekaran 的解法，原话是：

“调一个独立的、天生持怀疑态度的评估器，比让生成器学会批判自己要容易得多。”

这是个结构性问题，不是措辞问题。你没法让一个作者跳出他自己的脑袋，但你可以引入另一个智能体，用完全不同的指令集，从零开始审视代码——不附带任何自我辩护的上下文。

这有点像 GAN：一个网络负责生成，另一个网络负责攻击——制造者和检查者。也像银行的古老规矩：汇款的人和批准汇款的人，必须是不同的两个人。

本课的任务——写两样东西：
在 .claude/agents/reviewer.md 里写一份评估器系统提示，包含五个板块：角色 + 假设 + 检查项 + 用什么工具 + 裁决。

声明这个循环的 /goal 终止条件——由独立的、全新的模型来判断，而不是由生成器自己说了算。

markdown
# .claude/agents/reviewer.md  （改三处）
角色：对抗性代码审阅者。
假设：在证明它没问题之前，这段代码默认就是**有毛病的**。
不要夸。只找问题。

# 修改：检查项的顺序要按你项目真正的故障模式来排，
# 能实际跑起来的检查排前面
检查项，按顺序：
  1. 它能跑吗？（执行它，而不是读代码）
  2. 测试：跑一遍，把真实输出贴出来。
  3. 作者漏掉的边界情况。
  4. 行为是否和工单描述一致？

# 修改：用哪个 MCP 取决于你在测什么——
# 前端 → Playwright，API → curl/httpie
用 Playwright MCP：打开页面，点击，
截图，检查 DOM。
判断实际行为，别信意图。

裁决：只有当所有检查项都通过 → 通过。
       否则 → 拒绝，并逐条列出原因。
bash
# 终止条件——由独立的小模型来判断，不是生成器
# 修改：替换成你那个事项真正的、可验证的条件
/goal all tests in test/auth pass and the lint step is clean

# 注意：/goal 和 /loop 不是一回事
#   /loop = 按间隔重新运行（没有终止判断——危险）
#   /goal = 一直跑到独立模型判断条件成立为止
最好是两个智能体、两个模型：“同一个模型换套提示词”通常还会保留同样的盲区。有条件的话，把模型也换掉。

默认怀疑：评估器的基线是“默认有毛病”——信任必须通过检查来挣得，不是默认就给的。

判断行为，而不是意图：“这 JSX 看着还行”和“我点了按钮，页面正常跳转了，这是截图”是两个完全不同的层次。评估器必须动手——跑测试、点页面，而不是读代码然后凭感觉点头。

带理由的拒绝：只说“拒绝”却不列理由，那不叫拒绝——生成器根本不知道往哪个方向修。

还有一块试金石：你的评估器在过去至少 5 轮里，真的拒过什么东西吗？一个在真实负载下跑了成百上千轮却一次都没说过“不”的循环，统计学上几乎不可能。如果真这样，只能说明你的评估器根本不在干活。

本课预防的陷阱：点头循环
循环在跑，智能体写代码，同一个智能体说“看着不错”。每一轮都自我批准，用机器的速度堆叠着看起来有理的垃圾。

修复：就是这一整课——结构分离 + 默认怀疑 + 动手验证 + 第三方终止条件。

你的评估器是“同一个模型换套提示词”，还是“彻底换了另一个模型”？为什么？

把“判断行为，而不是意图”翻译成你项目里一句具体的话：
“我的评估器不读代码——它跑 _____，只有当它看到 _____ 时，才给通过。”

一个“差不多凑合”的独立模型，有多大可能会错误地通过你的 /goal 条件？

第 4 课 持久化：让今天的工作活到明天
第 3 课跑完了。你的评估器审了三个事项——两个通过，一个拒绝。问题来了：这三个裁决结果现在存哪儿了？

如果答案是“在上下文窗口里”——那明天早上 6 点，循环一醒来上下文全刷新，什么都不记得。它会从头重新分流一遍，被昨天没修的那个拒绝再绊一跤，可能又派一个智能体再去修一遍，也可能直接漏掉，还可能掉进同一个坑里。

这就是失忆循环——每天都从同一格起跑。

解药只有一句话：记忆是落盘的状态，不是窗口里的上下文。 一个 markdown 文件、一个 Linear 看板、一个数据库——只要写下来，智能体忘得再干净都无所谓。

这两个概念经常被搞混，所以钉死：

上下文 = 智能体本轮看到的窗口 -> 每次刷新就清空。

记忆 = 跨轮次、跨天存活的状态 -> 落盘（markdown / DB / 看板）。

循环通过记忆来衔接今天和明天。

本课的任务：
创建 ./state/triage.md，至少包含 4 列（事项 / 来源 / 优先级 / 状态）——第 1 课的技能负责写它，第 2 课的工作树负责读它。

接上连接器（MCP）：通过裁决自动开 PR，拒绝裁决自动更新工单。

验证明天的循环确实能把今天的状态读回来。

markdown
# ./state/triage.md  （循环的记忆——按需调整）

| 事项            | 来源       | 优先级 | 状态     |
|-----------------|------------|--------|----------|
| auth 测试不稳定  | CI #4821   | P0     | 修复中   |
| 空指针解引用     | issue 92   | P1     | PR 已开  |
| 过时依赖         | commit a3f9c | P2   | 收件箱   |

# 按需扩展列：最后查看时间、重试次数、指派给谁
# 这个文件必须提交到仓库 ——
# 否则明天的云上运行器根本看不到它
json
// .mcp/connectors.json — 把循环对接到外部系统
{
  "github_pr": {
    "type": "mcp",
    "on_event": "evaluator.verdict.PASS",
    "action": "open_pr",
    "branch": "fix/${slug}",
    "auto_merge": false        // ← 必须是 false。人工闸门在第 5 课
  },
  "linear": {
    "type": "mcp",
    "on_event": "evaluator.verdict.REJECT",
    "action": "update_ticket",
    "fields": { "status": "Blocked", "reason": "${verdict.reasons}" }
  }
}
为什么每一列都有用：没有来源 -> 你没法追溯这个事项从哪来的。没有优先级 -> 你没法安排先后。没有状态 -> 明天接不上棒。

这一课的验证是你唯一没法靠脑补完成的：等到明天再说。 醒来，查一下——收件箱还在吗？未完成的事项状态还保留着吗？早上 6 点的运行是从昨天停下的地方继续，还是又从零开始了？这个问题只能靠实际跑一轮来回答，靠推理是推不出来的。

持久化一旦跑通，一个新陷阱就打开了：循环以极快速度往外吐 PR，你感觉很高效——但你对代码库的心理地图却在无声无息地过时。规则很简单：不要每份都读（那循环就白搭了），但每天至少读一个样本 PR，逼自己讲清楚循环改了啥、为什么改。

当你发现自己讲不清楚的时候——你的地图已经落后了。在平静的早晨花十分钟就能补上。在生产事故里补，成本要高得多。

本课预防的陷阱：失忆循环
循环找到了有价值的事，干了，然后忘了自己干过——因为结果只活在已经被刷掉的上下文里。下一轮它重新发现同样的事，更糟的是可能重做一遍，把第一次的成果给覆盖了。

症状：没有任何积累，每天都从零开始。

修复：状态文件落盘。

继续之前，回答这三个问题：
把“记忆 ≠ 上下文”翻译成你项目里一句具体的话：
“我的 _____ 是记忆，我的 _____ 是上下文。”

明天的循环醒来——它会先读 state.md 的哪一列来决定第一步动作？你给那列取对名字了吗，还是你给它埋了个雷？

纪律问题：你每天会在什么时间读那一份样本 PR？
现在就设个日历提醒——这是你跟自己签的约。

第 5 课 调度：让它落地，让它安全，留一扇门
第 1～4 课都装好了，但循环在你停止按“运行”按钮的那一刻就停了。最后一步只有一个动词：把它挂在一个触发器上。

但这课最危险的地方不是写错 cron。恰恰相反——是把 cron 写对了。因为一旦写对，循环就真的开始独立运转了，一个 bug 能让它整夜打转，助手衍生助手，直到你早上醒来看到一张你不认识的账单。

所以这一课实际上干三件事：挂触发器、设上限、留一个人工入口。

第一步——选你的调度器：
云上（GH Actions）	本地定时任务	/loop（在 CC 内）
跑在哪	云端	你的机器	你的机器
机器要开着吗	不需要	需要	需要
会话要开着吗	不需要	不需要	需要
最小间隔	1 小时	1 分钟	1 分钟
能访问本地文件吗	否	是	是
决定性的问题是：这个工作能不能离开你的笔记本？

“每分钟检查一次我的本地开发服务器” → 必须是本地 + /loop（云的 1 小时间隔够不到它）

“凌晨 3 点扫 GitHub 议题并开 PR” → 必须是云端（你笔记本合着——循环没法等你）

整个实践里最隐蔽的一种自欺欺人是：把本地定时器当成“睡觉时也在跑”。其实它不是，它只是“趁我还在的时候多跑几轮”。

本课的任务：
编写 .github/workflows/triage.yml，用 cron 触发器来启动晨间分流技能。

设三个上限：单次运行超时、每日预算、最大重试次数。

工作流以这条规则收尾：PR 永不自动合并，任何拿不准的东西丢进 ./inbox/。

yaml
# .github/workflows/triage.yml  （改三处）
name: morning-triage

on:
  schedule:
    - cron: '0 6 * * *'        # 修改：你时区 06:00 对应的 UTC 时间

jobs:
  triage:
    runs-on: ubuntu-latest
    timeout-minutes: 45          # ← 单次运行上限 · 修改
    permissions:
      contents: write
      pull-requests: write
    steps:
      - uses: actions/checkout@v4

      - name: morning triage
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          DAILY_BUDGET_USD: '20'   # ← 每日预算上限 · 修改
          MAX_RETRIES: '3'          # ← 重试次数上限 · 修改
        run: |
          claude --skill morning-triage \
            --max-retries "$MAX_RETRIES" \
            --daily-budget-usd "$DAILY_BUDGET_USD"

      - name: 开 PR（永不自动合并）
        run: |
          # PR 自动开。合并保留给人。
          gh pr create --draft --base main \
            --title "[loop] $(date +%F) triage" \
            --body-file ./state/triage.md
          # 这里故意没有 `gh pr merge`

      - name: 拿不准的走收件箱
        run: |
          ls ./inbox/ && echo "有东西等人来审"
让它在六个月后仍然活着的三条规则：
上线之前，先设上限：三个层级——单次运行超时、每日预算、最大重试次数——在第一次真正独立运行之前设好，而不是在看到第一张惊人账单之后。令牌上限不是用来省钱的，它是一个断路器，把“开放式风险”变成“有界风险”。没有上限的循环，等于把自己的花钱权限外包给了自己的 bug。

参考一下规模：Uber 在四个月内烧光 AI 预算后，把工程师的额度卡在每人每工具每月 1500 美元。你的单循环上限就是那个教训的粒度版本。

永远留一扇门：PR 不自动合并。拿不准的东西落到收件箱。你每天读一份样本。这扇门的存在，不是因为人每天都会走进去，而是因为门开着，你才始终保有走进去的能力。把每一扇门都焊死，等哪天你需要进去的时候，钥匙已经丢了。

验证它真的会醒。至少让它跑满 3 轮（试跑也算）。最常见的翻车现场：演示那天惊艳全场，周四就彻底凉了。“最后一次运行就是演示那天”——这是手动循环的典型诊断特征。

在 Claude Code 之外也一样跑——这些能力不绑定具体厂商，只是名字不同：
能力	Claude Code	Codex
调度	/loop · worker	Automations tab
跑到条件为止	/goal	automation rerun + judge
并行隔离	--worktree	background worktree
子智能体	.claude/agents/	.codex/agents/
外部连接	MCP + plugins	MCP connector
显式技能	SKILL.md	$skill-name
机器离线运行	Cloud Routines	cloud（planned）
问题从来不是“选哪家”，而是六个能力是不是都装到位了。

本课预防的陷阱：手动循环
四个动作搭得漂漂亮亮，唯独没有 cron。它不是一个循环——它是一个你跑了一次就忘了的脚本。

修复：挂上任何一个不依赖于你“记得去按”的触发器。

正式上线之前，回答这三个问题：
你的三个上限具体是多少？
如果一个 bug 整夜空转——哪个上限会第一个跳出来挡住它？如果一个都挡不住……这说明什么？

你的人工入口长什么样？
（PR 审阅 / 收件箱 / 每日样本 / 每周对账？）写下来 = 跟自己签个契约。

收尾问题：六个月后，这个循环会让你变得更强（理解更深、判断更准、对系统更有感觉）——还是让你退化成一个你根本看不懂的机器的看管人？你打算怎么避免后一种情况？

四种隐性债务和“始终做工程师”
你的循环已经组装就绪：它会醒，会找活干，会自我批评，会记住，会调度明天的自己。

但循环跑起来之后，有四样东西会悄无声息地积累——它们共同的可怕之处在于，没有一样会主动报警。

验证债务	没被拒绝的输出在持续堆积
理解衰退	代码库在涨，你的心理地图没动
思维惰性	“我不太想仔细审了，就这样吧”
令牌爆表	一个 bug 空转一整夜 → 你看到一张账单
它们互相喂养：没被验证的输出侵蚀你的理解 → 被侵蚀的理解滋生惰性 → 惰性让循环跑更久、花更多钱 → 产出更多没被验证的输出。

在循环第一次独立运行之前，对照这四项做个审计：

我的评估器真的会拒绝——它不只是个摆设

我每天读一份样本 PR，并且能讲清楚改了啥

我保留了说“这个不对”的习惯

我的上限是在第一次跑之前设的，不是在收到第一张账单之后

而真正决定走向的，是下面这个：
同一个循环，两个人搭，可能走向截然相反的终点。 一个人用它来提速，但仍然坚持读代码、把控方向——循环放大了他已有的判断力。

另一个人用完全相同的循环，唯一目的就是再也不碰任何理解层面的东西——六个月后，第一个人更锐利了，第二个人成了他看不懂的机器的保姆。

Addy Osmani 说得好：“把循环搭起来，但要以‘始终是一线工程师’的姿态去搭——而不是仅仅做那个按‘开始’的人。”

循环让“生成”变得几乎免费，真正稀缺的仍然是判断力：哪个方案是对的，在哪一行停下来，哪个东西能跑但根上是错的。循环不会贬低判断力——它剥掉一切不属于判断力的东西，只留下它本身。

循环是一个忠实的放大器：
你带着理解力来——它放大理解力。
你带着惰性来——它放大惰性。
在动手之前，先想清楚你打算放大哪一边。
