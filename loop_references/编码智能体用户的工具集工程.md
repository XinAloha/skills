编码智能体用户的工具集工程
为了让编码智能体在更少监督下工作，我们需要方法来增强对其结果的信心。作为软件工程师，我们对 AI 生成的代码存在天然的信任屏障——LLM 是非确定性的，它们不了解我们的上下文，它们实际上也不理解代码，它们以 token 方式思考。本文探讨一种心智模型，将上下文工程和工具集工程中涌现的概念结合起来，以构建这种信任。

2026 年 4 月 2 日

“工具集”（harness）这个术语已经成为一个简写，指代 AI 智能体中除模型本身之外的一切——智能体 = 模型 + 工具集。这是一个非常宽泛的定义，因此有必要针对常见的智能体类别进行收窄。我想在此斗胆，在“使用编码智能体”这个有限上下文中定义其含义。在编码智能体中，工具集的一部分已经内置了（例如通过系统提示、或选定的代码检索机制、甚至是复杂的编排系统）。但编码智能体也为作为用户的我们提供了许多功能，来为我们的特定用例和系统构建一个外部工具集。

隐喻的局限性
有人向我指出，在工具集外面再套工具集是没有意义的：“你试过把工具套装在狗的里面吗？”所以这有点牵强，但只要它能帮助我们驾驭这个词的用法，我乐意接受。

图 1：三个同心圆，核心是模型（最终被工具集驾驭的东西），往外一圈是编码智能体的构建者工具集，最外层是编码智能体的用户工具集。

“工具集”一词根据有限上下文的不同而具有不同的含义。

一个构建良好的外部工具集服务于两个目标：它提高了智能体一开始就做对的概率，并且它提供了一个反馈循环，在问题甚至到达人类眼前之前，就让智能体尽可能多地自我修正。最终，它应该减少审查负担，提高系统质量，附带的好处是沿途浪费更少的令牌。

前馈与反馈
为了驾驭编码智能体，我们既要预测并防范不希望的输出，又要设置传感器以允许智能体自我修正：

指南（前馈控制）——预测智能体的行为，并在其行动之前引导它。指南提高了智能体在第一次尝试时产生好结果的概率。

传感器（反馈控制）——在智能体行动后进行观察，并帮助其自我修正。当它们产生为 LLM 消费而优化的信号时尤其强大，例如包含自我修正说明的自定义 linter 消息——这是一种积极意义上的提示注入。

单独来看，你要么得到一个重复犯同样错误的智能体（仅有反馈），要么得到一个编码了规则但从未发现它们是否有效的智能体（仅有前馈）。

计算型 vs 推理型
指南和传感器有两种执行类型：

计算型——确定性的、快速的，由 CPU 运行。测试、linter、类型检查器、结构分析。在毫秒到秒级内运行；结果可靠。

推理型——语义分析、AI 代码审查、“LLM 作为法官”。通常由 GPU 或 NPU 运行。较慢且更昂贵；结果更加非确定性。

计算型指南通过确定性工具提高好结果的可能性。计算型传感器成本低且速度快，可以伴随着智能体在每次变更时运行。推理型控制当然更昂贵且非确定性，但它们允许我们提供丰富的指导，并增加额外的语义判断。尽管存在非确定性，当与强大的模型（或者说适合当前任务的模型）一起使用时，推理型传感器尤其能增强我们的信任。

工具集工程与上下文工程的关系？
上下文工程为我们提供了让指南和传感器对智能体可用的手段。为编码智能体构建用户工具集是上下文工程的一种特定形式。

调控循环
人类在此工作中的任务是通过迭代工具集来引导智能体。每当一个问题发生多次时，就应该改进前馈和反馈控制，使该问题在未来发生的可能性更低，甚至完全阻止它。

在调控循环中，我们当然也可以使用 AI 来改进工具集。编码智能体现在使得构建更多定制控制和定制静态分析变得便宜得多。智能体可以帮助编写结构测试、从观察到的模式生成规则草案、搭建自定义 linter，或从代码库考古中创建操作指南。

时机：保持质量左移
持续集成的团队一直面临挑战：根据成本、速度和关键性，将测试、检查和人工作审阅分布在开发时间线上。当你追求持续交付时，你理想上甚至希望每个提交状态都是可部署的。你希望检查尽可能放在通往生产路径的左侧，因为越早发现问题，修复成本越低。反馈传感器，包括新的推理型传感器，需要相应地分布在生命周期中。

变更生命周期中的前馈与反馈
哪些是相当快的，应该在集成之前甚至提交创建之前就运行？（例如 linter、快速测试套件、基础代码审查智能体）

哪些更昂贵，因此只应在集成后的流水线中运行，同时重复快速控制？（例如变异测试、可以考量全局的更大范围代码审查）

在变更生命周期中的前馈示例：LSP、architecture.md、/how-to-test skill、AGENTS.md、可访问团队知识管理工具的 MCP 服务器、/xyz-api-docs skill；它们输入到智能体的初始生成中；第一次自我修正循环的反馈传感器示例：/code-review、npx eslint、semgrep、npm run coverage、npm run dep-cruiser；然后人工审查是额外的反馈传感器；接着集成；集成之后，在流水线中重新运行所有之前的传感器，额外更昂贵的传感器示例：/architecture-review skill、/detailed-review skill、变异测试。箭头表示反馈随后可以导致智能体或人类的新提交。

持续漂移与健康传感器
哪些类型的漂移是逐渐积累的，应该由持续针对代码库运行的传感器监控，在变更生命周期之外？（例如死代码检测、测试覆盖质量分析、依赖扫描器）

智能体可以监控哪些运行时反馈？（例如让它们查找退化的 SLO 并提出改进建议，或让 AI 法官持续抽样响应质量并标记日志异常）

变更集成后的持续反馈传感器示例：代码库中的持续漂移检测，例如 /find-dead-code、/code-coverage-quality、dependabot；或持续运行时反馈，例如延迟、错误率或可用性 SLO 触发编码智能体建议，或 /response-quality-sampling、/log-anomalies AI 法官。

调节类别
智能体工具集就像一个控制论的调节器，结合前馈和反馈来将代码库调节到其期望状态。区分期望状态的多个维度是很有用的，按工具集应该调节什么来分类。区分这些类别有帮助，因为“可工具集化”和复杂度在这些类别之间有所不同，并且用词更精确可以让我们有一个更准确的语言来描述这个本来非常宽泛的术语。

下面是我认为目前有用的三个类别：

可维护性工具集
我在本文中给出的大约所有示例都是关于调节内部代码质量和可维护性的。这是目前最简单的一类工具集，因为我们有很多现有的工具可以用于此。

反思一下这些前述的可维护性工具集想法在多大程度上增加了我对智能体的信任，我将之前编目的常见编码智能体故障模式与它进行了对照。

计算型传感器可靠地捕获结构性问题：重复代码、圈复杂度、缺失的测试覆盖率、架构漂移、风格违规。这些是廉价的、成熟的、确定性的。

LLM 可以部分解决需要语义判断的问题——语义上的重复代码、冗余测试、暴力修复、过度工程化的解决方案——但代价高昂且概率性。不是每次提交都能做到。

两者都不能可靠地捕获一些影响更大的问题：问题误诊、过度工程和不必要的特性、误解指令。它们有时能捕获，但不足以降低监督需求。如果人类没有明确指定他们想要什么，正确性就在任何传感器的职责范围之外。

架构适配性工具集
这组指南和传感器定义并检查应用程序的架构特征。基本上就是：适配性函数。

示例：

向前传递我们性能要求的技能，以及向智能体反馈其是否改进或退化的性能测试。

描述更好可观测性的编码约定（如日志标准）的技能，以及要求智能体反思其可用日志质量的调试说明。

行为工具集
这是房间里的大象——我们如何引导和感知应用程序的功能行为是否符合我们的需求？目前，我看到大多数赋予编码智能体高度自主权的人这样做：

前馈：一份功能规格说明（详细程度不一，从简短提示到多文件描述）。

反馈：检查 AI 生成的测试套件是否变绿，覆盖率是否合理较高，有些人甚至用变异测试监控其质量。然后结合人工测试。

这种方法在 AI 生成的测试上寄托了很大信心，这还不够好。我的一些同事在“已批准夹具模式”上看到了良好结果，但它更适用于某些领域而非其他领域。他们有选择地在合适的地方使用它，这不是测试质量问题的通用解决方案。

所以总体来说，我们还有很多工作要做，才能为功能行为设计出足够好的工具集，使我们的信心提高到足以减少监督和人工测试。

工具集简化概述：水平方向显示指南和传感器，垂直方向显示调节维度：可维护性、架构适配性、行为。行为工具集的示例：规格作为前馈指南，测试套件作为混合推理型和计算型的反馈传感器，加上表示人工审查和手动测试作为主要额外反馈传感器的人类图标。

可工具集化
并非所有代码库都同样适合工具集化。用强类型语言编写的代码库自然拥有类型检查作为传感器；明确定义的模块边界支持架构约束规则；像 Spring 这样的框架抽象掉了智能体甚至不需要担心的细节，因此隐式地提高了智能体成功的概率。没有这些属性，这些控制就无法构建。

环境便利性
我的同事 Ned Letcher 使用“环境便利性”（ambient affordances）一词来描述智能体环境中使其更易于工具集化的属性：“环境本身的结构性属性，使其对在其中运行的智能体来说具备可读性、可导航性和易处理性。”

这在绿地项目与遗留项目中有不同体现。绿地团队可以从第一天就内置可工具集化——技术决策和架构选择决定了代码库的可治理性。遗留团队，尤其是那些积累了大量技术债务的应用程序，面临更困难的问题：工具集在最需要的地方最难构建。

工具集模板
大多数企业有几种常见的服务拓扑，覆盖了他们 80% 的需求——通过 API 暴露数据的业务服务；事件处理服务；数据仪表板。在许多成熟的工程组织中，这些拓扑已经以服务模板的形式编码了。未来这些可能会演变为工具集模板：一组针对特定拓扑的结构、约定和技术栈的指南和传感器，将编码智能体“拴”住。团队可能开始部分基于已有的工具集来选择技术栈和结构。

艾什比定律
艾什比定律（Ashby's Law of Requisite Variety）是支持这些预定义拓扑的另一个有趣论点。该定律指出，调节器必须至少具有与其调节的系统一样多的多样性，并且它只能调节它有模型的东西。基于 LLM 的编码智能体几乎可以产生任何东西，但承诺采用一种拓扑可以缩小这个空间，使全面的工具集更易实现。定义拓扑是一种减少多样性的举动。

我们当然会面临与服务模板类似的挑战。一旦团队实例化它们，它们就会开始与上游改进脱节。工具集模板将面临同样的版本管理和贡献问题，甚至可能更糟，因为非确定性的指南和传感器更难测试。

人的角色
作为人类开发者，我们将自己的技能和经验作为隐式工具集带入每个代码库。我们吸收了约定和良好实践，感受到复杂性的认知痛苦，并且知道我们的名字在提交上。我们还携带组织一致性——了解团队试图实现什么、哪些技术债务因业务原因被容忍、以及在这个特定上下文中“好”长什么样。我们以小步幅和人类的节奏前进，这为经验被触发和应用创造了思考空间。

编码智能体完全没有这些：没有社会责任感，不会对一个 300 行的函数产生审美厌恶，没有“我们这里不这样做”的直觉，也没有组织记忆。它不知道哪个约定是承重墙、哪个只是习惯，也不知道技术上正确的解决方案是否符合团队的目标。

工具集是试图将人类开发者经验所带来的东西外化和显式化，但它只能做到这一步。构建一个连贯的指南、传感器和自我修正循环系统是昂贵的，所以我们必须带着明确的目标来优先排序：一个好的工具集不一定旨在完全消除人工输入，而是将其引导到我们的输入最重要的地方。

一个起点——以及开放问题
我在此阐述的心智模型描述了已经在实践中发生的技术，并有助于围绕我们仍需弄清楚的方面构建讨论。其目标是将对话提升到功能层面之上——从技能和 MCP 服务器，到我们如何战略性地设计一套控制系统，使我们对智能体产出的东西产生真正的信心。

以下是当前讨论中一些与工具集相关的示例：

OpenAI 的一个团队记录了他们的工具集长什么样：通过自定义 linter 和结构测试强制实现分层架构，以及定期的“垃圾回收”扫描漂移并让智能体建议修复。他们的结论是：“我们现在最困难的挑战集中在设计环境、反馈循环和控制系统上。”

Stripe 关于他们“小兵”的写书记述了如基于启发式运行相关 linter 的 pre-push 钩子，他们强调了“左移反馈”对他们的重要性，以及他们的“蓝图”展示了他们如何将反馈传感器集成到智能体工作流中。

变异测试和结构测试是过去未充分利用的计算型反馈传感器示例，但正在重新兴起。

开发者中关于在编码智能体中集成 LSP 和代码智能的讨论越来越多，这是计算型前馈指南的示例。

我听到 Thoughtworks 团队的故事，他们同时使用计算型和推理型传感器来解决架构漂移，例如通过混合智能体和自定义 linter 提高 API 质量，或通过“清洁工大军”提高代码质量。

还有很多问题需要解决，不仅仅是已经提到的行为工具集。我们如何在工具集不断增长时保持其连贯性，确保指南和传感器同步且不相互矛盾？当指令和反馈信号指向不同方向时，我们能在多大程度上信任智能体做出合理的权衡？如果传感器从不触发，这代表高质量还是检测机制不足？我们需要一种方法来评估工具集的覆盖范围和质量，类似于代码覆盖率和变异测试对测试所做的那样。前馈和反馈控制目前分散在交付步骤中，确实存在工具化的潜力来帮助配置、同步和将它们作为系统进行推理。构建这个外部工具集正在成为一项持续的工程实践，而不是一次性配置。
