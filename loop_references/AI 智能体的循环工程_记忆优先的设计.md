AI 智能体的循环工程：记忆优先的设计
循环工程是设计、实现和调优控制循环的实践，该控制循环决定了 AI 智能体如何随时间与环境交互。它关注智能体如何读取上下文、规划、行动、观察结果，以及在多步之间更新其内部状态。

大多数 LLM 工作流最初被设计为单次提示。然而，生产环境中的智能体通常会运行数百或数千步，往往跨越多个会话和用户。循环工程就是让这些长时间运行的循环可靠、高效，并与产品目标保持一致。

任何循环内部的一个核心挑战是记忆。智能体需要记住之前发生了什么、用户偏好什么、以及已经尝试过什么。这就是像 Mem0 这样的结构化记忆层如何改变循环形态的地方。

令牌充裕 vs 令牌匮乏的循环
循环工程通常始于一个设计选择：模型在每一步应该看到多少上下文？

令牌充裕的循环（Token-rich loop）
令牌充裕的循环是指每次迭代在提示中包含大量上下文的循环。例如：

完整的对话记录

详细的工具调用日志

长文档或代码库

嵌入的计划和子目标

优点：

模型拥有高分辨率的历史视图

由于缺失上下文导致的错误更少

关于模型“知道”什么的推理更简单

缺点：

每步令牌成本高

响应慢

上下文窗口溢出的风险

难以扩展到大量用户或长时间会话

令牌匮乏的循环（Token-poor loop）
令牌匮乏的循环是指每次迭代包含最少上下文的循环。例如：

只有最后 2-3 条消息

简短摘要而非原始日志

少量检索到的记忆而非完整历史

优点：

令牌使用量更低

响应时间更快

更容易保持在上下文限制内

缺点：

更多幻觉和重复工作

智能体忘记重要细节的风险更高

需要更好的记忆和摘要基础设施

循环工程是在令牌充裕和令牌匮乏之间找到平衡的艺术，由延迟、成本、质量和安全需求驱动。

为什么开发者应该关注循环工程？
循环设计直接影响：

可靠性：智能体会在工作流中途忘记关键的用户约束吗？

成本：你每次请求是否为数千个无关令牌付费？

延迟：因为提示词太大，用户每次响应要等 10 秒吗？

安全性：智能体是否有正确的历史上下文来避免有害或不一致的行为？

在实践中，许多团队从令牌充裕的方法开始，因为它简单。所有东西都塞进上下文窗口。随着时间推移，他们发现：

由于上下文头部被截断，模型仍然会遗忘

随着使用规模扩大，账单显著增长

关于智能体应该记住什么，没有清晰的结构

这时，循环工程就成了优先事项，构建或采用记忆系统变得至关重要。

智能体循环的核心组件
展示了生产级智能体循环的主要阶段以及信息如何在它们之间流动，使控制周期变得具体。

在高层次上，一个生产级智能体循环涉及以下阶段：

1. 输入捕获
用户消息或环境事件

元数据，如用户 ID、时间、渠道

2. 上下文组装
最近的交互历史

检索到的长期记忆

系统指令和工具

任务特定上下文

3. 模型推理
使用组装好的提示进行 LLM 调用

可选的函数/工具调用检测

4. 行动执行
工具调用、API 请求、数据库操作

对外部系统施加的效果

5. 观察与日志记录
行动的结果

错误或异常

对未来决策相关的细节

6. 记忆更新
决定应该存储什么

写入短期和长期记忆

可能进行摘要或压缩

循环工程就是让这些阶段显式且可调优的过程，而不是让它们通过单个长提示隐式地涌现。

循环内部的记忆问题
没有适当的记忆层，智能体往往会：

反复问用户同样的问题

丢失长时间运行的任务的进度

忘记偏好和约束

重复失败的策略

跨会话产生不一致的响应

常见的临时解决方案包括：

将整个聊天日志推入提示

将所有内容存储在向量数据库中并按相似性检索

为特定工作流手写摘要

这些方法有帮助，但留下了几个空白：

没有“用户级”与“任务级”记忆的结构化概念

没有关于存储或检索什么的自动决策

没有记忆的权限或所有权模型

在不重写记忆代码的情况下，难以更换模型或调整循环设计

这正是 Mem0 设计要解决的问题空间。

Mem0 如何融入循环工程
Mem0 提供了一个智能记忆层，直接嵌入循环中，处理：

存储什么：它可以从原始文本、工具输出和事件中提取有意义的记忆。

如何存储：它在内部管理嵌入、元数据和模式。

检索什么：它可以根据当前上下文搜索、过滤和排序记忆。

跨什么范围：它支持用户级、智能体级和全局记忆。

一个使用 Mem0 的智能体循环大致遵循以下模式：

接收用户输入。

向 Mem0 查询与该用户和任务相关的记忆。

组装提示，包含：系统指令、工具、检索到的记忆、最近的交互和用户消息。

调用 LLM 并执行任何行动。

将输出和选定的事件发回 Mem0 以更新记忆。

通过将记忆移入专用层，循环变得更加令牌高效且更易于推理。智能体不需要整个原始历史，它只需要 Mem0 返回的精炼记忆。

示例：使用 Mem0 的令牌匮乏循环（Python）
可视化使用 Mem0 的令牌匮乏循环示例，展示检索和存储如何围绕精简的模型调用展开。

以下示例展示了一个简单的对话智能体，它使用 Mem0 来维护长期用户记忆，同时保持每个提示令牌匮乏。

首先安装依赖：

bash
pip install mem0ai openai
然后创建 Python 脚本：

python
import openai
from mem0 import Memory

# 初始化 Mem0
mem0 = Memory()

# 初始化 OpenAI 客户端
client = openai.OpenAI()

def run_agent(user_id, user_message):
    # 1. 检索相关记忆
    memories = mem0.search(
        query=user_message,
        user_id=user_id,
        limit=5
    )
    
    # 2. 组装上下文（令牌匮乏）
    context = "相关记忆：\n"
    for m in memories:
        context += f"- {m['text']}\n"
    
    # 3. 构建提示
    prompt = f"""
    你是 AI 助手。使用以下上下文回答问题。

    {context}

    用户：{user_message}
    助手："""
    
    # 4. 调用 LLM
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": prompt}]
    )
    
    answer = response.choices[0].message.content
    
    # 5. 存储新记忆
    mem0.add(
        text=f"用户说：{user_message}。助手回复：{answer}",
        user_id=user_id
    )
    
    return answer
这个循环明确是令牌匮乏的：

它不传递整个对话历史

它只从 Mem0 检索一小组相关记忆

它使用简单规则决定何时写入记忆

同样的模式可以扩展到工具、多步工作流或多智能体系统。

循环工程模式的局限性
循环工程和记忆层并不能消除所有挑战：

提示质量仍然重要：即使有了强大的记忆，糟糕的系统提示或工具规格也会导致错误。循环工程不能取代基本的提示和 API 设计。

记忆策略可能出错：决定存储和检索什么并非易事。糟糕的策略会用噪音堵塞记忆，增加检索歧义并损害响应质量。

概念漂移和过时记忆：用户改变偏好，系统改变行为，任务也在演变。循环必须包含更新或丢弃过时记忆的策略。

调试复杂性：多步、记忆感知的循环可能更难追踪。工程师需要可靠的日志、回放和评估工具来推理失败原因。

令牌匮乏的循环并不总是理想的：有些任务确实需要丰富的本地上下文，如编辑长文档或多文件代码变更。在这些情况下，循环工程是关于将本地上下文与检索到的记忆混合，而不是不惜一切代价最小化令牌。

Mem0 处理记忆管理层，但循环工程仍然需要围绕模型、工具和产品需求进行深思熟虑的设计和评估。

常见问题
问：在 AI 智能体的上下文中，什么是循环工程？
循环工程是设计智能体遵循的控制周期的实践，以读取上下文、推理、行动和随时间更新状态。它关注使该周期可靠、高效并与产品目标保持一致，以便智能体在多步中表现一致。

问：循环工程与提示工程有何不同？
提示工程优化单个模型调用，而循环工程优化这些调用如何被串联以及状态如何在它们之间被管理。提示工程在请求层面工作，循环工程在跨多个请求和会话的系统层面工作。

问：AI 团队应该在什么时候开始关注循环工程？
一旦智能体需要处理多步任务、持久化用户偏好或跨会话行为，循环工程就变得重要。如果提示词正在不受控制地增长，且响应随时间变得不一致，这通常是一个信号，表明需要循环工程和记忆设计。

问：为什么记忆对循环工程如此核心？
没有显式的记忆，智能体能看到的唯一状态就是适应当前提示上下文窗口的内容。记忆提供了步骤之间和会话之间的连续性，允许智能体记住偏好、进度和先前的决策，这对于现实的、生产级的循环至关重要。

问：Mem0 如何改进令牌匮乏的循环？
Mem0 让智能体检索一组紧凑的相关记忆，而不是将整个历史发送给模型。这使得提示保持小巧，同时保留重要上下文，从而在不牺牲个性化和任务连续性的情况下降低成本和延迟。

问：Mem0 可以与不同的智能体框架和模型一起使用吗？
Mem0 作为一个独立的记忆层，可以与任何能调用其 API 的框架或自定义循环集成。它是模型无关的，因此团队可以在保持相同记忆行为的同时更换模型或智能体编排代码。
