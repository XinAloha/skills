循环工程
2026年6月7日

循环工程，就是用系统设计来取代“你本人亲自去提示智能体”这个角色。你设计一套系统，让它来干这件事。这里的“循环”，可以理解为一个递归的目标：你定义一个目的，然后AI反复迭代直到完成。我觉得这很可能是未来我们与编码智能体协作的方式。不过现在还在早期阶段，我持保留态度，而且你必须小心令牌成本（用量模式在令牌充裕和令牌紧张时差异巨大），所以我想把这件事拆开来说清楚，它到底是什么、意味着什么。

Peter Steinberger 最近说：“你不应该再亲自去提示编码智能体了。你应该设计循环，让循环来提示你的智能体。”类似地，Anthropic 旗下 Claude Code 的负责人 Boris Cherny 也说：“我不再提示 Claude 了。我有循环在跑，是它们在提示 Claude 并自己决定下一步做什么。我的工作是写循环。”

好，那这些话到底是什么意思？

过去差不多两年里，你从编码智能体那里得到产出的方式，就是写一条好提示词，塞足够的上下文。你敲一段话，读返回的结果，再敲下一段。智能体是一个工具，你全程握着它，一轮接一轮。那个阶段基本已经结束了，或者至少有些人认为它要结束了。

现在，你构建一个小系统：它自己找活干、派发出去、检查结果、记录已完成的内容，然后决定下一步做什么。你让这个系统去调用智能体，而不是你自己亲自上。我之前写过它的近亲——智能体工具集工程，那是关于单个智能体运行的环境，以及工厂模型——即构建软件的系统。循环工程则位于工具集之上的一层。还是那个工具集，但它按定时器运行，能生成小的辅助任务，并且能自我驱动。

让我感到意外的是，这已经不是工具层面的问题了。一年前，如果你想做一个循环，你得写一堆bash脚本，然后永远维护那堆东西，它是你的，也只能是你的。现在，这些部件直接内置在产品里了。Steinberger 列出来的那张表，几乎原样映射到 Codex 应用上，然后又几乎一样地映射到 Claude Code 上。一旦你发现这个结构是相同的，你就不会再争论用哪个工具了——你只需要设计一个循环，无论你坐在哪个工具面前，它都能照常工作。

五个部件，以及一些备注
一个循环需要五样东西，再加上一个用来记事情的地方。我先列出来，然后再展开。

自动化任务：按计划自动运行，自己完成发现和分流。

工作树：让两个并行工作的智能体不会互相踩脚。

技能：把项目知识写下来，省得智能体每次都靠猜。

插件和连接器：把智能体接到你已经用起来的工具上。

子智能体：一个负责出方案，另一个负责检查。

然后是第六样东西——记忆。一个markdown文件，或者一个Linear看板，任何存在于单次对话之外、记录已完成内容和下一步计划的东西。听起来太简单了，好像不值一提。但这是每个长期运行的智能体都依赖的同一个技巧，我在写长期运行智能体那篇文章时深入聊过：模型在每次运行之间会忘记一切，所以记忆必须存在磁盘上，而不是在上下文里。智能体会忘，仓库不会。

现在这两个产品（Codex 和 Claude Code）都已经具备了全部五个部件。

自动化任务——这是心跳
自动化任务，是让循环真正成为“循环”的东西，而不是你跑过一次就完事的一次性运行。在 Codex 应用里，你在 Automations 标签页创建一个自动化任务，选择项目、要跑的提示词、运行频率，以及它是跑在你本地检出版本上还是后台工作树上。那些发现了东西的运行会进入 Triage 收件箱，啥也没发现的运行就自动归档，这个设计不错。OpenAI 内部用它来做一些乏味的事，比如每日议题分流、汇总 CI 失败、写提交简报、查上周别人引入的 bug。而且自动化任务可以调用技能，所以你让周期性的东西保持可维护性——你触发 $skill-name，而不是把一堵巨大的指令墙贴进一个永远不会有人更新的调度里。

Claude Code 通过调度和钩子到达同一个目的地。你可以用 /loop 按间隔运行一条提示词或一条命令，可以调度一个 cron 任务，可以在智能体生命周期的特定节点用钩子触发 shell 命令，或者如果你想让它在合上笔记本后继续跑，就把整件事推到 GitHub Actions 上。完全相同的思路：你定义一个自治任务，给它一个节奏，然后发现的结果会主动送到你面前——你不需要自己到处去查。

还有一个值得了解的会话内原语，它更接近这篇文章的核心。/loop 按固定节奏重新运行。/goal 则持续运行，直到你写的某个条件真正成立为止，每一轮结束后会有一个独立的小模型来检查你是否已完成——所以写代码的那个智能体不会给自己打分。你给它类似“test/auth 下所有测试通过且 lint 干净”这样的条件，然后就可以走开了。Codex 也有同样的东西，也叫 /goal，它会跨轮次持续工作，直到一个可验证的停止条件成立，支持暂停、恢复和清理。同一个原语，两个工具都有——这差不多就是整篇文章的基调了。

所以，这部分是把工作“浮出水面”的环节。循环的其余部分则是对这些工作采取行动。

工作树——让并行不至于变成混乱
一旦你运行了超过一个智能体，文件就开始撞车——这就会变成故障。两个智能体写同一个文件，和两个工程师没人打招呼就提交到同一行代码上，是一样的头疼事。git worktree 解决了这个问题：它是一个独立的工作目录，在自己的分支上，共享同一个仓库历史，所以一个智能体的编辑在物理上就不可能碰到另一个智能体的检出版本。

Codex 内置了工作树支持，多个线程可以同时命中同一个仓库而互不干扰。Claude Code 用 git worktree、--worktree 标志（在独立检出版本中打开会话）以及 isolation: worktree 设置（放在子智能体上，让每个助手获得一个独立检出版本，用完自动清理）提供了同样的隔离能力。我在《编排税》那篇文章里写过这件事的人性面——工作树消除了机械冲突，但你仍然是天花板，你的审阅带宽决定了你实际上能跑多少个，而不是工具决定的。

技能——省得你每次都重新解释你的项目
技能解决了你每次会话都像金鱼一样重新解释项目上下文的问题。两个工具用同样的格式：一个文件夹，里面有一个 SKILL.md，包含指令和元数据，然后还可以有可选的脚本、参考资料和资源。Codex 在你用 $ 或 /skills 调用技能时运行它，或者当你的任务匹配到技能描述时自动运行——这就是为什么一个严谨、平淡的描述比一个花哨的聪明的更好。Claude Code 用同样的方式，我之前在《智能体技能》那篇文章里写过这个模式。

技能还让“意图”不再一遍又一遍地消耗你。我在《意图债务》里说过，智能体每次会话都是冷启动的，它会用自信的猜测来填补你意图中的任何空洞。技能就是写在外部的那份意图——那些约定、构建步骤、“因为那次事故我们不要这样做”，写一次，智能体每次运行都读。没有技能，循环每一轮都从零推导你整个项目；有了技能，它会不断累积。

有一件事要搞清楚：技能是创作格式，插件是分发方式。当你想要跨仓库共享一个技能，或者把几个技能打包在一起时，你把它们打包成一个插件。Codex 如此，Claude Code 亦如此。

插件和连接器——循环触碰你真正的工具
一个只能看到文件系统的循环，是个很小的循环。连接器（基于 MCP 构建）让智能体能够读取你的议题追踪器、查询数据库、访问 staging API、在 Slack 里丢一条消息。Codex 和 Claude Code 都支持 MCP，所以你为一个工具写的连接器通常能在另一个里直接工作。插件则将连接器和技能打包在一起，这样你的队友一次安装就搞定了你的整套设置，而不必凭记忆重建所有东西。

这就是“智能体说‘这是修复方案’”和“循环自己开 PR、关联 Linear 工单、CI 变绿后自动 ping 频道”之间的区别。连接器让循环能够在你真实的环境里行动，而不只是告诉你“如果它能的话它会怎么做”。

子智能体——让制造者和检查者分开
循环里最有用的结构性设计，毫无疑问是把写代码的人和检查代码的人分开。写了代码的那个模型给自己的作业打分时，手太松了。一个带着不同指令（有时是不同模型）的第二个智能体，能抓到第一个自己把自己说服过去的东西。

Codex 只在你要求时才生成子智能体，它们同时运行，然后把结果汇聚回一个答案中。你在 .codex/agents/ 里把自己的智能体定义为 TOML 文件，每个有名称、描述、指令，以及可选的模型和推理强度——所以你的安全审阅者可以是一个高强度的大模型，而你的探索者则是一个快速的只读小模型。Claude Code 用 .claude/agents/ 里的子智能体和在它们之间传递工作的智能体团队做同样的事。两者常见的分工是：一个智能体探索，一个实现，一个对照规格做验证。

我提过这个观点两次了，一次是《代码智能体管弦乐队》，一次是《对抗性代码审阅》。它在循环里特别重要的原因是：循环在你没看着的时候也在运行，所以一个你真正信任的验证者，是你敢走开的唯一理由。子智能体确实会烧更多令牌，因为每个都做自己的模型调用和工具调用，所以要把它们花在“第二个意见值得付费”的地方。这基本上也是 Claude Code 的 /goal 在底层做的事——一个全新的模型决定循环是否完成，而不是做事的那个模型——制造者和检查者的分离，应用到了停止条件本身。

一个循环长什么样
把这些拼在一起，单条线程就变成了一个小控制面板。下面是我一直在用的一种形态。

每天早上，一个自动化任务在仓库上运行。它的提示词调用一个分流技能，读取昨天的 CI 失败、未关闭的议题、最近的提交，把发现写入一个 markdown 文件或 Linear 看板。对每个值得做的发现，这条线程打开一个独立的工作树，派一个子智能体去起草修复，然后第二个子智能体根据项目技能和已有测试来审阅那份草稿。

连接器让循环能够打开 PR 并更新工单。循环处理不了的东西落到分流收件箱里等我来处理。状态文件是整个系统的脊柱，它记住什么已经试过了、什么通过了、什么仍然开着——所以明早的运行能从今天停下的地方继续。

然后你看看你实际上做了什么。你设计了一次。你没有亲自提示其中任何一步。这就是 Steinberger 那番话的真实落地，而且它在 Codex 和 Claude Code 里是同一个循环，因为部件是一样的。

循环仍然不能替你做的事
循环改变了工作方式，但它不会把你从工作中移除。而且有三个问题，在循环变得更好的时候，反而会变得更尖锐，而不是更轻松。

验证仍然在你身上。 一个无人值守运行的循环，也是一个在无人值守时犯错的循环。把验证子智能体和制造者分开的全部原因，就是要让循环的“完成了”有点分量——但即便如此，“完成了”仍然是一个主张，而不是一个证明。我一直在重复《AI 时代的代码审阅》里的同一句话：你的工作是交付你确认过能跑的代码。

你的理解力如果放任不管，仍然会衰退。 循环交付你没写过的代码越快，代码库实际存在的东西和你真正理解的东西之间的鸿沟就越大。这就是理解债务，一个顺畅的循环只会让它增长得更快——除非你去读循环产出的东西。

那种舒适的姿态是危险的。 当循环自己跑起来的时候，你很自然地会停止持有观点，它给什么你就接什么。我把这个叫做认知投降。用判断力去设计循环时，它是解药；用循环来避免思考时，它是催化剂。同样的动作，相反的结果。

把循环搭起来，但始终做那个工程师
我觉得这大概是我们工作方式演变的预览。话虽如此，如果我自己不审阅代码，或者完全依赖自动化循环来修复问题，我的产品质量一定会下滑。我很可能会陷入一个恶性循环，不断把自己挖进更深的坑里。

话说回来，尽管去搭你的循环，但别忘了直接提示智能体也同样有效。关键是要找到那个平衡点。

循环产生的结果也会因你而不同。两个人可以搭出完全相同的循环，却得到截然相反的结果。一个人用它来在自己深入理解的工作上提速。另一个人用它来避免理解工作。循环分辨不出两者的区别。但你能。

这就是为什么循环设计比提示工程更难，而不是更简单。Cherny 的观点不是说工作变轻松了，而是说杠杆点转移了。

把循环搭起来。但要以“始终是一线工程师”的姿态去搭——而不仅仅是那个按“开始”的人。
