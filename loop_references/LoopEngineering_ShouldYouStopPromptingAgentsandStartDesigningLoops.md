循环工程：你应该停止提示智能体，转而设计循环吗？
Hiba Fathima
2026年6月11日

这个月，一句六个英文单词的话让科技圈推特陷入了一场混战。Peter Steinberger 在 2026 年 6 月 7 日发了这条帖子：

你不应该再亲自提示编码智能体了。你应该设计循环来提示你的智能体。

这条帖子获得了 220 万次浏览，而评论区则演变成了一场关于它到底意味着什么的争论。推特之外的反馈也同样两极分化。在 Reddit 上一个询问“循环工程”是否是 AI 开发下一个热门词汇的帖子里，开发者们的观点从“这真的是下一个抽象层”到“这不就是个戴了顶帽子的 cron 任务”摇摆不定。

开发者们对于循环工程究竟是下一个真正的抽象层，还是仅仅是换了个名字的 cron 任务，意见分歧很大。

两天前，Claude Code 的构建者 Boris Cherny 在台上给出了对这个想法最干净利落的表述：

我不再直接提示 Claude 了。我现在跑着一些循环。是它们在提示 Claude 并自己决定下一步做什么。我的工作是写循环。

那么，什么是循环？为什么大家都在争论它？当你真正搭建一个的时候它长什么样？下面是实践者视角的版本。

循环工程到底是什么
在过去两年的大部分时间里，和编码智能体协作的感觉就像一场高强度的乒乓球赛。你精心雕琢一条指令。你等待。你浏览返回的内容，调整措辞，再发下一条。你的注意力就是引擎。一旦你离开键盘，智能体就在半途中冻结了。

循环工程，就是让你不再做那个引擎。

你写一个小程序——有时是一个 shell 循环，有时是一个托管任务，有时是几百行 TypeScript——然后那个程序去跟模型对话。它挑选下一个任务，派发出去，给返回的结果打分，记录结果，然后决定是否再来一轮。模型不再是聊天窗另一端的协作者了；它变成了程序在 while 循环里调用的一个函数。

Addy Osmani 的框架在这里很有用：提示工程是一层。智能体工具集工程——设计单个智能体运行的环境——是上面一层。循环工程则位于工具集之上的一层。工具集仍然重要，但循环跑在它上面，按计划运行，生成辅助任务并自我驱动。

Shann Holmberg 画出了它出现的两种规模。在小型的一端，一个智能体反复走过研究、起草、自我审阅和修订的流程，直到产出达标为止。在大型的一端，一个编排器把一个目标切分成多个块，把每个块分发给一个专家智能体，而这些专家智能体又各自依赖自己的助手。机制是相同的，变化的只是人头数。

任何循环的核心都是同样的四步周期：行动 → 观察 → 推理 → 重复。智能体做一件事，读取返回的结果，对照目标决定这意味着什么，然后决定是否再来一轮。其他一切（调度、工作树、子智能体、状态文件）都是围绕这个周期的脚手架。

提示工程 vs 智能体工作流 vs 循环工程
这三个词经常被混用，但它们不应该被混用——就像之前这个周期里“提示工程 vs 上下文工程”的混淆一样。下面是它们真正的区别：

提示工程	智能体工作流	循环工程
你做什么	为单轮交互写一条好的提示词	用分支逻辑串联多步调用	设计一个替你提示智能体的系统
自主性	无。你坐在驾驶座上	中等。预定义步骤，模型填充空白	高。按计划运行，直到停止条件成立
最适合	单次任务、内容生成、简单查询	结构清晰、形状已知的流水线	开放式、迭代式、路径不完全确定的工作
你在优化	提示词	工作流链	循环本身及其内部的标准
你的任务真的适合做成循环吗？
知道分类是一回事；知道你的具体任务是否属于那一类，是另一回事。在动手搭建循环之前，用三个条件来检验一下：

重复性。你做这件事足够频繁，设计系统的成本能收得回来。

可验证性。“完成”可以被表达为一个智能体或验证子智能体能实际执行的检查。如果你无法定义“通过”长什么样，循环就不会知道什么时候该停。

价值性。产出值得消耗那些令牌。循环在时间和金钱上有一个地板成本。琐碎的工作过不了这个门槛。

如果一个流程同时满足这三条，它就值得做成循环。如果缺了其中一条，你通常最好手动提示，或者写一个常规脚本。

一个能正常运行的循环的解剖结构
每一个能在生产环境中存活的循环，都解决了同一组问题：它什么时候运行？并发的智能体如何互不干扰？它们带什么知识进场？工作如何分工和验证？循环如何触达你技术栈的其余部分？如何交接给队友？以及跨运行之间记住了什么？Codex 和 Claude Code 给这些部件起了不同的名字，但职责是匹配的。

触发器。总得有个东西启动一次运行，而且不能是你亲手打字。在 Codex 里这是 Automations 标签页——选一个仓库、一条提示词、一个调度计划、一个沙箱，运行结果排队进入 Triage。在 Claude Code 里，它是 /loop、/goal、定时任务、钩子和 GitHub Actions 的某种组合。触发器必须附带一个停止条件；我们后面会讲到它长什么样。

并发智能体之间的隔离。一旦两个智能体同时触碰同一个检出版本，你就会遇到两种故障模式之一：静默覆盖，或者剧烈冲突的合并。Git 工作树通过给每个智能体自己的分支和自己的工作副本解决了这个问题，它们共享同一个仓库。现在两个工具集都能帮你拉起工作树。如果让智能体并行运行却没有工作树，那你就是在制造一个竞态条件。

智能体不必重新发现的编码化上下文。一个“技能”——即一个包含 SKILL.md 以及所需脚本和夹具的文件夹——是项目特定知识在运行之间存活下来的方式。当技能 frontmatter 里的描述匹配到任务时，智能体就会加载它；大部分人正是在这个描述上搞砸的。把它写得像一句标语，而不是一篇宣言。Codex 和 Claude Code 的技能格式相同。

子智能体之间的分工。回本最快的循环模式，是把写代码的人和审阅代码的人分开。一个智能体（或一串联的子智能体）做出改动；另一个独立的智能体（通常用一个更精简的模型）对照项目规则和它能跑的测试来给它打分。审阅者不必比写作者更聪明——它只需要不同，有自己的指令和自己的评判标准。

连接器。一个被困在工作目录里的循环，充其量是一个被美化的脚本。连接器是它触达其他一切的方式：议题追踪器、staging API、数据仓库、Slack、你的监控栈、实时网页。它们跑在 MCP 上，Codex 和 Claude Code 都支持 MCP，所以你为一个工具集设置的连接器，通常可以直接套用到另一个工具集里，不需要重写。这就是“智能体递给你一个补丁让你自己去打”和“循环自己开 PR、关联 Linear 工单、在 #engineering 频道发帖、自己等 CI 变绿”之间的分界线。

插件。Claude Code 插件和它们在 Codex 里的对应物，比连接器再往上走一层：它们把一组连接器和知道如何使用它们的技能打包在一起，这样队友就可以用一条命令安装你整套循环设置，而不必从你的仓库里反向工程出来。连接器是线缆；插件是线缆加说明书。

比进程活得更久的记忆。如果循环记不住昨天做了什么，上面一切都不重要。存储形式故意做得很朴素：仓库里的 markdown 清单、旁边的 JSON 文件、Linear 看板、SQLite 数据库。选一个，让每次运行在开始时读取它，在结束时追加写入。这就是循环如何在崩溃、上下文窗口重置或凌晨 3 点进程被杀后存活下来的方式。

开放式循环 vs 封闭式循环
Holmberg 还画出了“开放”与“封闭”的区分，这是我在选择循环形态时见过的最有用的维度。

开放式循环用结构换取覆盖面。你给智能体一个目标和一些护栏，让它自己选择穿越问题的路线。非常适合原型设计或未知领域。代价是：如果项目标准模糊，产出基本上全是噪音。

封闭式循环翻转了契约。你先画出路线——每一步做什么、怎么检查、循环什么时候允许停止——然后智能体在这个脚手架内部迭代。运行时成本保持可预测，结果往往会随时间改善，因为每一轮都对照同一套标准来打分。

在生产环境中，封闭式循环是默认赢家。你让一个循环负责目标，把步骤分配给专用智能体，把狭隘的苦活向下推给子智能体，然后让一个自动化检查来决定什么能通过。开放式循环值得运行的时候，是你还在摸索工作本身是什么的阶段，或者在那些烧令牌本身就是目的的个人项目上。

为什么让循环停下来是最难的部分
关于循环工程的浪漫版本是：你写好了循环，一千个智能体一夜之间帮你建起了公司。生产环境中的版本是：你写好了循环，然后你大部分工作变成了确保它们会停下来。

随便点开一个关于这个话题的讨论串，大多数开发者提出的第一个顾虑都是令牌成本，而不是架构。在同一个 Reddit 帖子里，最高赞的回复都是关于失控开销的：人们分享那些在夜间静默吞噬了数百美元的循环账单，问大家“除了在公司报销账户下，普通人怎么负担得起这个？”

大多数开发者对循环最想知道的，不是“怎么搭建”，而是“怎么不让它清空我的账户”。

这个顾虑是对的，修复方案也毫无光环可言：每个循环要么带着硬性防护上线，要么就别上线。

Uber 在四个月内烧完了年度 AI 预算后，把工程师在 Claude Code 和 Cursor 上的使用额度卡在了每人每工具每月 1500 美元。开销从“写代码”转移到了“运行那个写代码的东西”上。今年的一些实践者文章不断落在同样的三道防护上：

迭代次数的硬上限，让一个卡住的循环无法一直空转。

差异检查，一旦最近几轮没有任何实质性变化就终止运行。

支出上限（按令牌或按美元），在账单追上你之前结束运行。

没有这三样，你跑的东西不叫循环。它叫一张未填写金额的发票。

第二个风险更安静，也更大。循环交付你没写过的代码越快，你的仓库里实际存在的东西和你真正理解的东西之间的鸿沟就越宽。Addy Osmani 称其为理解债务，循环跑得越好，债务积累得越快——除非有人真的在读那些经过的差异。验证的责任在你身上。“完成了”是一个主张，不是证明。

还有第三个风险，是没有人会提前指出的：一个没有品味在背后的循环。Greg Brockman 最近提出了这个问题的更广泛版本：随着模型能力持续增强，输出的瓶颈不再是模型本身，而是操控它的人的品味。

这几乎可以逐字应用到循环上。循环会放大你投入评判标准、技能和验证步骤中的任何判断力。这三样东西必须反映真正的品味：在你的代码库里“好”意味着什么、哪些边界情况真正重要、什么时候某样东西真正准备好上线而不仅仅是技术上“通过”。当它们做到的时候，循环会朝正确的方向复利增长。当它们没做到的时候，你只是搭建了一条更快的路径来交付不值得做的工作：更多没人读的文档、更多没人要的 PR、更多基于错误根因而自动关闭的工单。循环让你以机器的速度犯错。循环工程奖励已经有了品味的人；工具集是容易复制的那部分，工具集内部的评判标准才是真正属于你的那部分。

Firecrawl 在循环中的位置
在每个能正常运行的循环里反复出现的模式是相同的：循环的质量取决于它内部的反馈质量。一个写了代码却没有反馈的开放式循环，就是一台生成自信错误的机器。

对于触及 Web 的循环（大多数生产环境循环最终都会触及 Web），反馈层就是Web 数据。循环在起草文案之前需要研究竞品。在针对一个快速迭代的 API 生成代码之前，它需要拉取文档页面。在重试之前，它需要检查状态页面。在决定对哪个条目采取行动之前，它需要从目录中提取结构化数据。

Firecrawl 就是为这一步而构建的。三个端点覆盖了循环所需的大部分场景：

search —— 返回一个查询的完整页面内容，而不仅仅是标题和摘要。

scrape —— 将任何 URL 转换为智能体可以推理的干净 markdown，包括 JavaScript 渲染的页面。

crawl —— 一次性拉取一个站点的整个部分。

从循环内部调用它们有两种方式：Firecrawl MCP 服务器作为连接器直接接入 Codex 和 Claude Code；Firecrawl CLI 让循环从 shell 步骤直接调用同样的端点。无论哪种方式，Firecrawl 都只是作为一个循环可以随时调用的工具出现。

有两种形态值得特别提一下。

第一种是“雄心勃勃的目标循环”。在 Claude Code 或 Codex 里给 /goal 一个真正困难的目标，让它跑起来。“真正困难”的具体例子：

“找出我们品类中所有公开竞品，按这五个维度打分，起草一份定位简报。”

“对照我们所依赖 SDK 最近六个次要版本的所有破坏性变更，审计我们的文档。”

智能体会持续搜索、抓取、阅读和修订，直到标准被满足。一个有真实范围的 /goal 运行可能需要很长时间才能完成，而 Firecrawl 就是那条补给线，让这个运行扎根于实时数据而不是模型记忆。

第二种是把 Firecrawl 本身作为触发器。monitor 端点监控一个 URL 或一组 URL，当内容发生变化时触发。把这个接入 Claude Code 钩子或 Codex Automation，你就有了一个以实时 Web为心跳的循环——定价页面变动触发竞品响应循环，API changelog 更新触发文档重写流水线，状态页面事故唤醒一个值班智能体。循环不是按固定计划轮询；它是在确实有新东西需要响应时才运行。

无论哪种形态，最终都落在同一个地方：一个内部调用了 Firecrawl 的循环，每次运行都不再猜测Web 上有什么——它读的是实际存在的内容。这就是让评判标准保持诚实、让技能保持有用的东西。归根结底，这也是让你昨天写的循环比明天要写的那个更有用的原因。

常见问题
什么是循环工程？

循环工程，是设计一个系统来替你提示编码智能体，而不是你自己去提示。你写一个小程序来处理发现、规划、执行、验证和迭代，这个循环按计划调用模型，直到停止条件达成。模型变成你循环内部的一个子程序，而不是提示框另一端的聊天伙伴。

循环工程和提示工程有什么不同？

提示工程优化的是单轮交互：一个输入，一个输出，一个人坐在驾驶座上。循环工程优化的是一个无需你参与的、运行多轮的系统。循环自己决定下一步问什么、读结果、对照目标检查，然后决定继续还是停止。你设计一次循环，让它自己跑，而不是整天打字敲提示词。

开放式循环和封闭式循环有什么区别？

开放式循环给智能体一个广阔的探索空间。它有一个目标但约束宽松，它可以尝试你没有指定的路径。它对于发现性工作很强大，但对你的令牌预算很残酷。封闭式循环是有边界的：一条已定义的路径、每一步的评估、一个清晰的停止条件。封闭式循环更便宜、更可预测，是生产工作的默认选择。

智能体设计中的封闭式循环是什么？

封闭式循环是指人类在循环运行之前就已经端到端设计好了路径的智能体循环。你定义每一步做什么、什么算通过、由哪个子智能体处理、循环什么时候允许停止。智能体仍然在循环内部迭代，但它们在固定的脚手架内迭代，而不是自己选择路径。封闭式循环是生产工作的默认选择，因为运行时成本可预测、产出可以对照稳定的标准打分、一个步骤的失败不会让整个目标偏离轨道。

我需要新工具来做循环工程吗？

不需要。这些原语已经内置在 Claude Code 和 Codex 里了。Claude Code 有 /loop、/goal、定时任务、钩子、工作树、技能、子智能体和 MCP。Codex 有 Automations、/goal、智能体技能、.codex/agents/ 里的子智能体和连接器。两者的形态是一样的。你设计一次循环，它可以在任何一个工具集里运行。

运行智能体循环的最大风险是什么？

一个停不下来的循环。如果没有显式的迭代上限、无进展检查和令牌/美元预算，一个智能体可以在一个周末烧掉一个计费周期。第二个风险是理解债务：代码落入了你的仓库，但你既没写过也不理解。循环的质量取决于它的验证步骤和停止条件。

Firecrawl 在循环中处在什么位置？

Firecrawl 是触及 Web 的循环的反馈层。当循环需要研究竞品、拉取文档页面、检查状态 URL，或在决定下一步之前从网站提取结构化数据时，Firecrawl 返回智能体可以推理的干净 markdown。没有新鲜外部上下文的循环会迅速退化。Firecrawl 就是让你保持循环扎根于现实的方式。

如何在智能体循环中使用 Web 搜索？

Web 搜索是循环的发现步骤。在智能体起草、调试或决定之前，它运行一个查询并读取实时 Web 返回的内容。Firecrawl 的 search 端点返回一个查询的完整页面内容，而不仅仅是摘要，所以循环有真实的文本来推理，而不是只有标题和 URL。模式很简单：拿着目标、推导出查询、调用 search、把顶部结果喂回循环的上下文，然后让下一步基于有依据的信息行动。跳过这一步的循环是在用过时的训练数据生成自信的答案。

如何在智能体循环中使用 Web 抓取？

当你已经知道 URL 时，Web 抓取就是循环的读取步骤。循环调用 Firecrawl 的 scrape 端点，获得干净的 markdown（包括 JavaScript 渲染的页面），然后把那段 markdown 作为上下文交给智能体做下一步决策。常见形态：在针对一个快速迭代的 API 生成代码之前抓取文档页面、在重试失败调用之前抓取状态页面、在起草文案之前抓取竞品页面，或在开 PR 之前抓取目录条目。把抓取和一个验证子智能体搭配使用，让它检查页面确实包含循环假设它应该包含的内容。
