# Language - 架构词汇表

本 skill 每条建议都用这个共享词汇。**严格使用这些词，不要替换为 "component / service / API / boundary"**。一致的语言就是关键。

## 术语

**Module（模块）**
任何"接口 + 实现"的东西。**刻意尺度无关**——同样适用于函数、类、包、跨层切片。
_避免_：unit、component、service。

**Interface（接口）**
调用方使用模块时**必须**了解的一切。包括类型签名，但还有不变量、顺序约束、错误模式、所需配置、性能特征。
_避免_：API、signature（太窄——只指类型层面的表面）。

**Implementation（实现）**
模块内部的代码。和 **Adapter** 区分：一个东西可以是"小适配器 + 大实现"（PostgreSQL 仓库），也可以是"大适配器 + 小实现"（内存 fake）。讨论 seam 时用 "adapter"，其他时候用 "implementation"。

**Depth（深度）**
接口处的杠杆——调用方（或测试）每学一份接口能获得多少行为。**深** = 大量行为藏在小接口后。**浅** = 接口几乎和实现一样复杂。

**Seam（接缝）** _(来自 Michael Feathers)_
能在不修改原地的情况下改变行为的地方；模块接口所在的位置。**选 seam 在哪里**本身就是设计决策，与"背后是什么"分开。
_避免_：boundary（与 DDD 的 bounded context 冲突）。

**Adapter（适配器）**
在 seam 处满足接口的具体实现。描述**角色**（填什么槽位），而不是**实质**（里面是什么）。

**Leverage（杠杆）**
调用方因深度获得的收益。每学一份接口换更多能力。一次实现回报到 N 个调用点和 M 个测试。

**Locality（局部性）**
维护者因深度获得的收益。变更、bug、知识、验证集中到一处，而不是散到调用方各处。**一次修，到处都修了**。

## 原则

- **深度是接口的属性，不是实现的属性**。深模块内部可以由小、可 mock、可换的部件组成——它们只是不属于接口。模块可以有**内部 seam**（私有于实现，自己测试用）和**外部 seam**（接口处）。
- **删除测试**。想象删掉这个模块。复杂度消失了 → 它没藏东西（透传）。复杂度跨 N 个调用方重现 → 它在挣它的工资。
- **接口就是测试面**。调用方和测试跨同一个 seam。如果你想测**接口之外**的东西，模块的形状大概是错的。
- **一个适配器 = 假想 seam；两个适配器 = 真 seam**。除非**真有东西在跨 seam 变化**，不要引入 seam。

## 关系

- 一个 **Module** 有恰好一个 **Interface**（呈现给调用方和测试的表面）。
- **Depth** 是 **Module** 的属性，对照其 **Interface** 度量。
- **Seam** 是 **Module** 的 **Interface** 所在地。
- **Adapter** 坐在 **Seam** 处、满足 **Interface**。
- **Depth** 给调用方产出 **Leverage**，给维护者产出 **Locality**。

## 被拒绝的框架

- **深度 = 实现行数 / 接口行数**（Ousterhout 原始定义）：奖励"灌水实现"。我们用"深度即杠杆"代替。
- **"接口" = TypeScript `interface` 关键字 / 类的 public 方法**：太窄——这里的接口包括调用方必须了解的每一个事实。
- **"Boundary"**：与 DDD 的 bounded context 冲突。说 **seam** 或 **interface**。
