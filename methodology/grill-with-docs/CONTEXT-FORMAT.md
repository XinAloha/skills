# CONTEXT.md 格式

## 结构

```md
# {上下文名称}

{一两句话说明这个上下文是什么、为什么存在}

## 语言

**前复权（forward adjustment）**：
对历史价格用最新除权信息回溯调整后的价格序列。
_避免_：除权调整、调权后

**采集器（Collector）**：
对接单一数据源、负责拉取并标准化字段的模块；不写库、不调度。
_避免_：抓取器、爬虫、Fetcher

**主数据源（primary source）**：
本项目优先尝试的数据源（默认 Tushare Pro），失败后降级到备源 / 降级源。
_避免_：第一数据源、首选 API
```

## 规则

- **要立场鲜明**。同一概念有多个词，挑最好的，把其他列在 `_避免_`。
- **定义要紧凑**。一两句话最多。定义"是什么"，不要写"做什么"。
- **只写本项目特有的术语**。通用编程概念（timeout、错误类型、工具模式）不要写进来——哪怕项目大量使用。判断：这个概念是本上下文独有，还是通用编程概念？只有前者属于这里。
- **自然成簇时分子标题**。如所有术语属于一个紧凑领域，平铺即可。

## 单 / 多上下文

**单上下文（多数仓库）**：根目录一个 `CONTEXT.md`。

**多上下文**：根目录 `CONTEXT-MAP.md` 列出各上下文位置和关系：

```md
# Context Map

## Contexts

- `data_collection/CONTEXT.md` — A 股行情、基本面与衍生数据采集
- `strategies/CONTEXT.md` — 回测与策略评估

## Relationships

- **Collection → Backtesting**: 通过 PostgreSQL 标准 schema 共享数据
```

skill 自动判断：

- 存在 `CONTEXT-MAP.md` → 读它找上下文。
- 只有根 `CONTEXT.md` → 单上下文。
- 都不存在 → 写第一条术语时**懒创建**根 `CONTEXT.md`。

多上下文存在时，先推断当前话题属于哪一个；不清楚就问。
