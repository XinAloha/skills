# ADR 格式

ADR（Architecture Decision Record）放在 `docs/adr/`，顺序编号：`0001-slug.md`、`0002-slug.md`……

**懒创建** `docs/adr/`——只在写第一份 ADR 时创建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：背景是什么、决定是什么、为什么。}
```

就这些。一份 ADR 可以只是一段。价值在于**记录"做了什么决定 + 为什么"**——不在于把每一节都填满。

## 可选小节

只在确实有用时加。多数 ADR 不需要：

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——决策需要重新审视时有用。
- **Considered Options** —— 被拒绝的方案值得记下来时。
- **Consequences** —— 非显然的下游影响。

## 编号

扫一下 `docs/adr/` 找最大编号，加 1。

## 何时该写 ADR

三件事都满足才写：

1. **难以反悔**：改主意的成本可观。
2. **没有上下文会觉得意外**：未来读者会想"为什么这么干？"。
3. **真有取舍**：真存在替代方案，你出于具体理由选了这个。

如果决策容易反悔，跳过——你后面会反悔的。如果不让人意外，没人会问。如果没有真正替代方案，没什么可记的，"我们做了显然该做的事"不需要 ADR。

### 哪些值得记

- **架构形状**："使用 monorepo"、"写模型用事件溯源、读模型投影到 PostgreSQL"。
- **跨上下文集成模式**："采集与策略通过 PostgreSQL 共享，而不是同步 HTTP"。
- **有锁定成本的技术选型**：数据库、消息总线、认证、部署目标。不是每个库——只有"换一次要花一个季度"的那种。
- **边界与范围决策**："标的代码格式以 Tushare 风格为准（`600519.SH`），其他源在采集器内部转换"。**显式的"不做什么"和"做什么"同样有价值**。
- **明显违背直觉的取舍**："手写 SQL 而不用 ORM，因为 X"。任何"合理的读者会以为应该反过来"的决策——能阻止下一个工程师"修复"一件其实是故意的事。
- **代码里看不到的约束**："不能用 AWS 因为合规"、"响应时间必须 < 200ms 因为合作伙伴 API 合同"。
- **被拒绝的方案——但拒绝的理由不显然**：考虑过 GraphQL 而选了 REST 的微妙理由——记下来，否则六个月后又会有人提议 GraphQL。

## 本项目示例（启动器）

- `0001-tushare-pro-为主数据源.md` —— 为什么选 Tushare 而非 AKShare 作主源。
- `0002-postgres-为生产存储.md` —— 为什么不用 ClickHouse / TimescaleDB。
- `0003-字段标准以-tushare-为准.md` —— 字段命名约定的取舍。
