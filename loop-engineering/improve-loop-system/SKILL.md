# 持续改良 Loop 系统

1. 聚合 journal、验证失败、人工审查、CI、运行时信号和成本数据；先去重并保留原始证据链接。
2. 按 [references/improvement-cycle.md](references/improvement-cycle.md) 分类：缺规范、缺传感器、缺工具/观测、缺权限边界、错误记忆、架构/流程失配或模型能力限制。
3. 将频发且可机械判断的问题优先转为测试、结构规则、lint 或策略检查；将稳定项目知识转为受审查文档；将不确定发现保留为实验，不写入长期记忆。
4. 为每项改进定义假设、责任人、最小变更、回归测试、成功指标与撤销条件。更新后运行相关验证，避免规则与传感器互相矛盾。
5. 定期运行 [references/drift-and-metrics.md](references/drift-and-metrics.md) 中的漂移扫描，审查从不触发的传感器、过时文档和成本异常。
6. 将已验证教训回写至对应 Skill、项目规则或脚本，并在状态/变更记录中附来源；不要让“临时聊天结论”成为隐式制度。

## 成功标准

每次系统改良都能追溯到证据并有回归验证；重复故障的发生率、检测时间或人工审查负担至少有一项得到可观测改善。
