# Tame Vibe Coding - Vibe Coding 债务控制模式

> **触发**：用户说"vibe coding / 认知债务 / 技术债务 / 提醒我别让 AI 跑偏 / 我有点看不懂这段代码了 / 别让我变 AI 代工厂"，或调用 `/tame-vibe-coding`。
>
> **核心理念**：Vibe Coding 的真正风险不是代码烂（那是技术债务），而是你**自己都不懂自己项目**了（认知债务）。本 skill 把开发者从"AI 代码生成器的下游工人"扳回"AI 代码的审查员和架构师"。AI 是工程师，你是架构师；AI 是实习生，你是 mentor。

## 一、先分清两类债务

| 维度 | 技术债务 (Technical Debt) | **认知债务 (Cognitive Debt)** ← AI 时代新问题 |
|---|---|---|
| **位置** | 代码本身 | 你和团队的大脑里 |
| **形态** | 硬编码、缺测试、临时方案 | "代码能跑但我说不清楚为什么这么写" |
| **后果** | 改代码困难、新 bug | 不敢改 / 新人上不了手 / 集体说不清系统怎么运作 |
| **时代** | 传统开发就有 | AI 让生成速度远超理解速度后才大规模出现 |

**认知债务的 4 个早期信号**（任意一条触发本 skill）：

- [ ] 我**不敢轻易改动**这段代码——明明是 AI 一周前帮我写的
- [ ] 新人/团队成员上手这块功能**比预期慢很多**
- [ ] 被问"这块为什么这么设计"时**说不清楚**
- [ ] 我**迷失在自己的项目里**了——不知道它能做什么、怎么运作

## 二、AI 审查员工作流（不是 AI 代工厂）

> **铁律**：AI 生成代码的速度，**必须慢于**你理解代码的速度。

### 1. 把 AI 当实习生，你是 Mentor

AI 生成的每一段代码，按**审查实习生 PR 的标准**对待：

- 这段逻辑是否符合项目约定（命名、错误处理、日志格式）？
- 边界条件有没有覆盖？空值、并发、网络失败？
- 有没有偷偷引入新依赖、新模式、新抽象？
- 性能/安全有没有隐患？

**不理解就合并 = 认知债务+1，且利息复利**。

### 2. 强制"复述验收"

合并 AI 代码前，要求自己（或团队成员）能用**几句话**复述清楚：

- 这段代码的**意图**是什么（解决什么问题）？
- 关键**逻辑**怎么走的？
- **边界**在哪（什么情况下会失败 / 什么情况下不该用）？

**说不出来 → 认知债务已产生 → 强制重新读懂或重写**，不许合。

### 3. TDD 优先：先让 AI 写测试，再写实现

| ❌ 反模式（AI 代工厂） | ✅ 正模式（AI 审查员） |
|---|---|
| 1. 让 AI 写实现 → 2. 跑一下能用 → 3. 合并 | 1. 我说需求 → 2. AI 写测试用例 → 3. **我审测试** → 4. AI 写实现 → 5. 测试通过 → 6. 合并 |

好处：
- **测试先 = 需求理解的早期对齐**，AI 理解错了在测试阶段就暴露
- **测试 = 偿还技术债务的安全网**，未来重构有保障
- 强迫 AI 先想清楚 contract 再写代码，逻辑会更干净

## 三、知识沉淀机制（对抗 AI 上下文遗忘）

> AI 的上下文是有限的：今天聊好的细节，明天它可能就忘了。**必须把知识固化到文件里**。

### 1. 维护 `Rules.md`（项目规则文件）

记录三类内容：

| 类别 | 例子 |
|---|---|
| **决策** | "采集器一律返回 DataFrame，不返回 dict" |
| **约定** | "时间字段命名统一用 `*_at` 结尾，DB 类型 timestamptz" |
| **教训**（从 bug 来） | "用户字段必须唯一；批量插入用 ON CONFLICT DO NOTHING" |

**关键习惯**：AI 每犯一次错，追问它一句——

> "我下次该**怎么问**才能让你一次做对？"

把它给出的答案（连同这条规则）写入 `Rules.md`。这样 AI 越用越"懂"你的项目，认知债务才不会复利。

### 2. 记录"生成轨迹"（关键 Prompt + AI 取舍 = 决策日志）

关键功能的实现，保留：

- 你最终用的**核心 Prompt**（不是中间瞎试的版本）
- AI 给的**关键取舍**（"用 A 方案而非 B 方案，因为……"）
- 你最后**采纳/否决**了什么

存放位置：`docs/decisions/` 或紧邻代码的 `*.decisions.md`。

**作用**：相当于 ADR (Architecture Decision Record) 的 AI 版本——让未来的你/同事 6 个月后还能搞懂"为什么这么写"，而不是只看到一堆"看起来合理但说不上为啥"的代码。

## 四、自动化护栏（减少低级错误）

让工具守住底线，把 AI 从重复性 review 中解放出来。**护栏不到位时不要让 AI 大量生成代码**。

| 工具类别 | 推荐工具（Python 项目） | 守住什么 |
|---|---|---|
| **静态分析** | `ruff` + `mypy` | 格式、import 顺序、类型错误、潜在 bug |
| **测试** | `pytest` + `pytest-cov` | 行为正确性、回归 |
| **CI/CD** | GitHub Actions / GitLab CI | 提交即跑测试 + lint + 类型检查 |
| **债务量化** | SonarQube / Code Climate | 复杂度、重复率、技术债务工时估算，**超阈值预警** |
| **依赖审查** | `pip-audit` / `safety` | AI 偷偷引入的有漏洞依赖 |

**进阶**：把 CI 失败信息回灌给 AI 让它自己修，形成"AI 生成 → CI 跑 → AI 看 CI 失败 → AI 自修"的自动化闭环。但**人必须在最终 merge 前做一次复述验收**，不能省。

## 五、核心思维转变（贴在工位前）

| 旧思维 | 新思维 |
|---|---|
| 从"**生成**" | 到"**理解**"（生成速度 ≤ 理解速度） |
| 从"**能用**" | 到"**可维护**"（6 个月后的你/同事能读懂） |
| 你是**写代码的人** | 你是**架构师**，AI 是工程师，你的核心价值是设计、决策、审查 |

## 六、本 skill 在本项目里的双向约定

本项目里，AI 和用户一起警惕 vibe coding 债务积累。本 skill 启用后：

- **AI → 用户**主动提醒的触发场景：
  - 用户让 AI 大量生成代码、却没要求 AI **先写测试**时 → 提醒走 TDD
  - 用户**没复述就准备合并**一段 AI 写的代码时 → 反问"用三句话说清这段在做什么/边界在哪"
  - 用户**反复让 AI 修同一个 bug** → 提示"是不是该把这个教训写入 `Rules.md`，下次让 AI 直接对齐"
  - 用户说"这段我看不太懂但能跑就先合了" → 强制 STOP，先复述验收
  - 项目里**没有 ruff / mypy / CI 护栏**就在批量生成代码 → 先建护栏再生成
  - 单次会话生成 **>200 行新代码** 没有对应测试时 → 警报
- **用户 → AI** 该要求的：
  - 关键功能先让 AI **写测试用例**（包含 happy path + 边界 + 失败）再写实现
  - 让 AI **解释自己写的代码**直到你能复述
  - 让 AI 在结束一段任务时**追加规则**到 `Rules.md`
  - 让 AI 给关键决策**留生成轨迹**（核心 prompt + 取舍 + 备选方案对比）

## 七、快速债务体检清单（每周做一次）

- [ ] 过去一周 AI 写的代码里，**有几段我现在已经说不清楚逻辑**？
- [ ] 项目里有 `Rules.md` 吗？过去一周更新过吗？
- [ ] 关键功能有"生成轨迹/决策日志"吗？
- [ ] `ruff` / `mypy` / `pytest` 在 CI 里全部绿吗？是不是有"先 skip 一下"留下的 TODO？
- [ ] 测试覆盖率有没有下滑？AI 加的新代码有没有对应测试？
- [ ] 有没有"不敢动"的模块？是哪个？什么时候安排重读 + 补测 + 补文档？
- [ ] 团队/我对系统架构的描述能保持一致吗？有没有人对某模块"说不清"？

如果**任意 3 项以上回答"是 / 不知道"**，停止新功能开发，先还债。
